# PRD: 냉장고 한 끼 (Fridge Meal)

## 1. 제품 비전

### 한 줄 요약

> 스마트 냉장고의 핵심 기능(재료 인식 + 레시피 추천)을 300만원짜리 냉장고 없이, 스마트폰 하나로 구현한 AI 레시피 앱.

### 기획 배경

#### 영감의 출발점: 스마트 냉장고

2026년 삼성 비스포크 AI 패밀리허브 냉장고는 구글 제미나이와 결합하여 냉장고 내부 카메라로 식재료를 자동 인식하고, 보유 재료 기반으로 레시피를 추천하는 'AI 푸드매니저' 기능을 제공한다. 하지만 이 기능을 사용하려면 최소 300만원 이상의 프리미엄 냉장고를 구매해야 한다.

#### 핵심 문제

- **"냉장고에 뭐가 있더라?"** — 매일 일어나는 보편적 문제
- **"이걸로 뭘 해먹지?"** — 식재료는 있는데 레시피를 모름
- **"또 이거 유통기한 지났네"** — 한국 가정의 연간 음식물 쓰레기 약 522만 톤
- **기존 레시피 앱의 한계** — 재료 입력이 귀찮고(수동 텍스트), 추천이 고정 DB 기반

#### 솔루션

스마트 냉장고의 데이터 라벨링(바코드/OCR) 기술을 스마트폰 카메라로 대체하고, 라벨링된 식재료를 드래그앤드롭으로 조합하여 AI가 실시간으로 맞춤 레시피를 생성하는 앱.

## 2. 타겟 사용자

### Primary: 자취생/1인 가구 (20~30대)

- 매일 "오늘 뭐 먹지?" 고민
- 배달 의존도 높지만 건강한 집밥을 원함
- 식재료 관리를 안 해서 유통기한 초과 폐기 빈번

### Secondary: 맞벌이 부부 / 워킹맘

- 남은 재료로 빠르게 한 끼 해결하고 싶음
- 유통기한 관리에 관심 많음

### Tertiary: 요리 초보

- 단계별 가이드 + 타이머가 있으면 도전 가능

## 4. 포트폴리오 관점

### 면접 어필 포인트

1. **카메라 + 드래그앤드롭 + AI** — 기존 포폴에 없던 기술 조합
2. **Flutter Draggable/DragTarget** — 모바일 인터랙션 깊이
3. **경쟁 분석 기반 차별화** — 시장 이해도 어필
4. **공공 API 활용 시리즈** — FuelKeeper + 냉장고 한 끼 = "공공 데이터 전문가"

## 5. 스코프

### MVP (v1.0) — 6주 (Supabase 셋업 1주 추가)

- **인증**: Supabase Auth (이메일 + Google/Kakao 소셜)
- 온보딩 3 스텝
- 내 냉장고 (재료 목록 + 카테고리 + 유통기한 뱃지)
- **재료 입력 3가지** (탭 전환):
  - 바코드 스캔 (Edge Function 프록시 → 식약처 API)
  - **자동완성 텍스트 입력 (신선식품용 — MVP 필수)**
  - 직접 입력
- 드래그앤드롭 → 항아리 조합
- AI 레시피 생성 (Edge Function 프록시 → OpenAI)
- 레시피 상세 (단계별 가이드 + 타이머)
- 유통기한 임박 알림 (로컬 푸시)
- 즐겨찾기 / 히스토리 (Postgres + Hive 캐시)
- 오프라인 모드 (Hive 캐시 폴백)

### v1.1

- 텍스트 OCR (바코드 없는 가공식품용 보조)
- 요리 완료 시 재료 자동 차감
- 통계 대시보드
- 가족 냉장고 공유 (Supabase Realtime)

### v2.0

- GPT Vision 이미지 인식 (재료 사진 → 자동 등록)
- 홈 위젯
- iOS 출시

## 6. 제약 사항

- 바코드 DB에 없는 제품은 자동완성/직접 입력으로 보완
- GPT API 비용 발생 (gpt-4o-mini 기준 레시피 1회 약 $0.002, 캐시 적중 시 0원)
- 음식 일러스트는 MVP 50개 + 카테고리 폴백 (200개는 v1.1)
- 포트폴리오 프로젝트지만 **출시급 품질**을 목표 (보안/확장성 고려)
- 안드로이드 우선 (iOS는 v2.0)

## 7. 확장성 고려 (가상 사용자 100만 명 가정)

> 포트폴리오에서 가장 강력한 어필 포인트.
> 실제 트래픽이 없더라도 "**100만 사용자라면 어떤 문제가 생기고, 어떻게 막는가**"를 설계에 반영한다.

### 7.1. 비용 추산

가정: DAU 10만 명, 1인당 일평균 1.2회 레시피 생성, GPT-4o-mini 1회 = $0.002

| 항목 | 캐시 없음 | 캐시 적중률 70% |
|---|---|---|
| 일일 GPT 호출 수 | 120,000회 | 36,000회 |
| 일일 비용 | $240 | **$72** |
| 월간 비용 | $7,200 | **$2,160** |

→ 캐시만 잘 짜도 **비용 70% 절감**. 면접에서 어필할 포인트.

### 7.2. 캐싱 전략

- **`recipe_cache` 테이블 (Postgres, 전역 공유)**
  - Key: `SHA-256(ingredients_sorted)`
  - 모든 사용자가 같은 캐시 풀 공유 → "양파+감자+돼지고기" 조합은 1번만 생성
  - TTL 7일, `hit_count` 기록으로 인기 조합 분석 가능

- **`barcode_cache` 테이블 (Postgres, 영구)**
  - 바코드는 변하지 않으므로 한 번 조회한 제품은 영구 캐시
  - 식약처 API 호출 횟수 99%+ 절감

### 7.3. Rate Limit (DDoS / 비용 폭주 방지)

- **유저별 일일 GPT 호출 한도: 10회 (무료)** — `api_usage` 테이블 카운팅
- 한도 초과 시 429 응답 + "내일 다시" 안내
- Edge Function 진입 시점에 검사 → OpenAI 호출 자체를 차단

### 7.4. DB 인덱스 전략

| 인덱스 | 목적 |
|---|---|
| `idx_ingredients_user_expiry (user_id, expiry_date)` | 홈 화면 정렬 (유통기한 순) |
| `idx_recipes_user_favorite` | 즐겨찾기 조회 (partial index) |
| `idx_cook_history_user_date` | 히스토리 페이징 |
| `idx_api_usage_user_func_date` | Rate Limit 카운트 |

### 7.5. RLS (Row Level Security)

- **모든 사용자 데이터 테이블에 RLS 적용** → 멀티테넌트 안전성
- 클라이언트가 anon key를 노출해도 다른 유저 데이터에 접근 불가
- 캐시/사용량 테이블은 RLS 미공개 (service_role만 접근, Edge Function 전용)

### 7.6. 콜드 스타트 / 가용성

- Supabase Edge Function (Deno) — 콜드 스타트 ~100ms (Lambda 대비 매우 빠름)
- AI 응답이 느릴 때 Flutter 측 타임아웃 15초 + 재시도 1회
- 오프라인 시 Hive 캐시(즐겨찾기/최근 레시피) 폴백

### 7.7. 모니터링 (포폴 PDF에 명시, 실제 셋업은 선택)

- Supabase Logs Explorer (Edge Function 호출/에러)
- Sentry (Flutter 크래시 + Edge Function 예외)
- 일일 비용 모니터: `api_usage` 테이블 합산 쿼리

### 7.8. 의도적으로 하지 않은 것 (포폴 인터뷰 답변용)

| 안 한 것 | 이유 / 대안 |
|---|---|
| Redis 캐시 | Postgres 캐시로 충분, 운영 복잡도↑ |
| 별도 BFF 서버 | Edge Function이 BFF 역할 |
| Realtime 동기화 | MVP 단일 디바이스 우선, v1.1에서 도입 |
| CDN | Supabase Storage가 자체 CDN 보유 (Cloudflare) |
| iOS | 1인 개발 리소스 한계, v2.0 |
